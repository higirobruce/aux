01 · Stack

The stack at a glance

Six layers, every choice locked. JavaScript / TypeScript everywhere it makes sense; Rust where it doesn't (the audio inner loop). Each row maps back to a commitment in brainstorm.html §16.

Rationale

The stack is biased toward TypeScript on both ends (same language, same types end-to-end). Rust appears in one place only — the DSP plugins — because there is no JS path to sample-accurate audio that doesn't compromise on safety, performance, or both. Every other layer is JS/TS.

02 · Frontend

Frontend architecture

Next.js 15 with the App Router. Marketing pages SSR on the edge for fast cold starts. The mixer itself loads as a single client-rendered surface from /session/[id] — no server roundtrip per parameter change.

Stack choices

Next.js 15
App Router

Marketing + auth + session shell. The mixer is a client component tree mounted under /session/[id].

Why: best React framework, server actions for mutations, edge runtime for fast cold starts, file-based routing, free image optimization. We don't fight the framework on data flow because we already use Yjs as the source of truth.

React 19
concurrent

useTransition for non-blocking UI on heavy renders (waveform redraw, plugin chain rebuild). useDeferredValue for the spectrum analyzer reading.

Why: the mixer renders 100s of components per frame at 60 fps. Concurrent React keeps the UI thread responsive while expensive renders complete.

Tailwind CSS 4
+ design tokens

The design system tokens (paper, ink, azure, type scale, spacing) loaded as Tailwind variables. Hand-rolled CSS reserved for the mockup islands (mixer, Smart EQ, Rooms).

Why: Tailwind 4 is fast and ergonomic for the 95% of the UI that's not exotic. For exotic components (knobs, faders, EQ canvas), explicit CSS gives the control we need.

Zustand
UI state

Selected channel, panel open/closed, current Reference Room, transport state.

Why: lighter than Redux, no boilerplate, plays well with React 19. Server state lives in TanStack Query; document state in Yjs.

SessionDoc
source of truth

The session document is a plain TypeScript object held in a Zustand-backed store with custom atom-path subscriptions. React subscribes via useAtom('trk_kick.volume'). Every parameter, every clip start, every plugin state is independently addressable per §16.02.

Why: v1 is solo-mixer (collab is v2+), so we skip the CRDT machinery and run the doc as a regular reactive store. Autosave debounces writes to disk (Local mode) or to the API (Cloud mode) every ~2 s. When real-time collab returns in v2, swap the storage backend for a Yjs Y.Doc — the atom-path API stays identical.

shadcn/ui
+ Radix primitives

Base UI: Button, Card, Dialog, Dropdown, Select, Switch, Tabs, Tooltip, Toast, Popover, Command (⌘K palette), Sheet (drawer), Table, Skeleton, Form, Input, Slider, Avatar, Badge. Installed via CLI as copy-paste source into packages/ui.

Why: built on Radix + Tailwind (already in our stack), so it composes without conflict. Copy-paste means we own the source — restyle once with our paper/ink/azure tokens, never fight the library again. Industry standard for new Next.js apps; new hires get zero ramp-up. The exotic mixing components (knobs, faders, meters, EQ canvas, channel strips, Reference Rooms, Stem swap, Pre-flight) stay hand-built — that's where the product's identity lives.

dnd-kit
timeline

Clip drag/resize on the timeline. Insert reorder. Send-slot reassignment.

Why: modular, accessible, modern. react-dnd is showing its age.

03 · Backend

Backend architecture

NestJS handles auth, session metadata, stem upload signing, the server-render fallback queue, and the public API. Hocuspocus runs as a separate process for Yjs sync — putting it inside Nest would couple WebSocket lifecycles to HTTP, and we want them independent.

Stack choices

NestJS 10
+ Fastify adapter

Module-per-domain: auth, sessions, stems, renders, billing. Each module owns its controllers, services, and DTOs.

Why: opinionated structure scales with the team; DI makes testing trivial; first-class TypeScript. Fastify over Express because it's 2–3× faster for our request shape (mostly signed-URL minting and JSON).

PostgreSQL 16
Neon serverless

Source of truth for accounts, session metadata, stem records, snapshots, collaborators. Schema below.

Why: Postgres is the boring correct answer. Neon's serverless model scales-to-zero, which suits the "free for everyone" cost story.

Prisma ORM
TS-first

Type-safe queries, migrations, and seed data. Schema lives in packages/db/schema.prisma.

Why: best DX in the TS ecosystem. Drizzle is a contender; Prisma's tooling (Studio, migrate) wins for our team size.

Redis
Upstash

Session presence (who's in which session), rate limiting on signed-URL minting, BullMQ queue backend, cached signed URLs (5-min TTL).

Why: Upstash's per-request pricing fits a low-baseline app. No idle server cost.

BullMQ
job queue

Server-side render fallback (when the user's machine can't), email sends, scheduled tasks (stem archive after 30 days).

Why: Redis-backed, NestJS module integration, battle-tested. No new infra.

better-auth
auth

Magic-link email auth by default. OAuth (Google, Apple) added when we need them. Sessions persisted in Postgres.

Why: more flexible than NextAuth, framework-agnostic, lighter than Auth0/Clerk. Hosting our own auth fits the "your data" ethos.

04 · Audio engine

Audio engine

The most engineering-risky piece. §16.01 specified the architecture; this section maps it onto concrete code. Three threads, one source of truth for the graph, lock-free communication via SharedArrayBuffer.

Threads & responsibilities

MAIN  (React, UI, Yjs)
  └─ session edit  ─→ postMessage to worker

WORKER (graph builder)
  ├─ deserialize session doc
  ├─ build node DAG · resolve send/return routing · compute latency
  ├─ shadow-render 2 blocks against new graph (validation)
  └─ signal AudioWorklet via SAB · "new graph at offset X is ready"

AUDIOWORKLET (real-time audio)
  ├─ on each process() call (128 samples):
  │   1. check SAB for pending graph swap  ─→ atomic pointer swap
  │   2. walk graph in topological order, calling plugin.process()
  │   3. write final stereo buffer to output
  └─ no allocations · no locks · no main-thread calls

Build pipeline

# DSP plugins: Rust → WASM
plugins/eq-8/src/lib.rs
  └─ cargo + wasm-pack
      └─ eq-8.wasm  + eq-8.d.ts  + eq-8-bindings.js

# Audio host: TypeScript → bundle
packages/audio-engine/worklet.ts
  └─ vite (worker-loader plugin)
      └─ audio-worklet.js  (loaded via AudioContext.audioWorklet.addModule)

packages/audio-engine/builder-worker.ts
  └─ vite
      └─ builder-worker.js  (loaded via new Worker())

The Plugin API contract

Every plugin exports the same four functions. Defined once in packages/audio-engine/plugin.d.ts:

interface PluginModule {
  init(sampleRate: number, maxBlock: number): number;  // pointer
  process(
    ptr: number,
    inputPtr: number,
    outputPtr: number,
    paramsPtr: number,
    nFrames: number
  ): void;
  setState(ptr: number, jsonPtr: number, len: number): void;
  getState(ptr: number): number;  // returns JSON ptr
  getSchema(): number;            // returns param schema JSON ptr
  latencySamples(ptr: number): number;
}

Parameter smoothing

Every parameter arrives at process() as a 128-sample array, not a scalar. The host pre-ramps from previous → target over 10 ms (≈ 480 samples at 48 kHz, ≈ 3.75 blocks). The plugin reads params[paramId][frame] for each frame, never branching on "did the value change."

This is what makes the design system's knob feel right: every twist is a smooth ramp, never a step.

05 · Async sharing

Async sharing

v1 is a solo-mixer. Real-time collab (Yjs, Hocuspocus, presence, WebRTC audio streaming) is explicitly v2+. What ships in v1 is the asynchronous version: snapshot the session, generate a share link, send it. The recipient gets a read-only viewer of that exact mix state — like sending a PDF of a mix.

What the recipient can do

  • Open the link without an account (anonymous, signed-token gated)
  • Play, pause, scrub the timeline
  • Switch reference rooms · view metering · view pre-flight results
  • Leave timestamped comments (v1.5)

What the recipient cannot do

  • Edit any parameter, fader, plugin, or clip
  • Save or export their own delivery
  • See the owner's other sessions

How it works

Owner clicks "Share" on a session
  ↓
POST /api/sessions/:id/share
  ├─ creates an immutable snapshot (full session doc, current state)
  ├─ mints a signed JWT containing snapshot_id + share_id
  └─ returns https://aux.app/share/<token>

Recipient opens the link
  ↓
Next.js /share/[token] route validates the JWT
  ├─ loads the snapshot from Postgres
  ├─ signs short-lived R2 URLs for the snapshot's stems
  └─ renders the mixer in read-only mode (UI props gate edits)

Owner revokes
  ↓
DELETE /api/share/:share_id
  └─ removes the share row · subsequent token validation fails

What this costs (in code and infra)

Nothing new. Snapshots already exist in the schema (§03). R2 signed URLs already work. The mixer UI gains one prop: readOnly. The /share/[token] route is one Next.js page. No WebSocket server, no Yjs, no CRDT, no WebRTC. The collab service (apps/collab) isn't built until v2.

v2 path is clear

When real-time collab arrives, the session document grows a Yjs layer over the same atom paths defined in §16.02. A second Fly.io app (apps/collab) runs Hocuspocus. Recipients of share links get an "upgrade to live session?" option. v1 sharing keeps working unchanged — it's additive.

06 · Storage layer

Storage layer

Two storage modes per §16.06. Each is a different code path inside a single abstraction — the StemStore interface. Hybrid mode returns in v2 alongside real-time collab. 

interface StemStore {
  putStem(file: File): Promise<StemRef>;
  getStem(ref: StemRef): Promise<AudioBuffer>;
  deleteStem(ref: StemRef): Promise<void>;
  listStems(): Promise<StemRef[]>;
}

// v1 implementations
class R2StemStore      implements StemStore { /* cloud  */ }
class FSAStemStore     implements StemStore { /* local  */ }
class OPFSStemStore    implements StemStore { /* safari fallback */ }

Cloud mode (R2)

  • Upload: browser POSTs to /api/stems/sign → receives a presigned R2 URL → uploads directly. Multipart for > 50 MB via the AWS SDK's S3 client (R2 is S3-compatible).
  • Download: signed GET URLs cached in Redis for 5 minutes. Range requests for partial loads (waveform preview without full download).
  • Tiering: R2 Infrequent Access after 30 days of no opens. Restore is instant (no Glacier-like wait) — R2 doesn't have a deep-archive tier, which is actually a feature for our use case.
  • Sharing: async share-links work here per §05. Signed JWT references a snapshot; recipient gets short-lived R2 URLs for that snapshot's stems.

Local mode (File System Access API)

  • Setup: on session create, showDirectoryPicker() asks the user to choose or create a session folder. Handle persisted in IndexedDB so it survives reloads.
  • Read/write: stems and session.json live in that folder. Reads via FileSystemFileHandle.getFile().
  • Fallback: Safari/Firefox without full FSA support get OPFS — a private, persistent, sandboxed filesystem. Same code shape, different backing store.
  • Sharing: not available. To share, export a snapshot bundle (stems + session.json zipped) or migrate the session to Cloud mode.

Hybrid mode (v2)

Returns alongside real-time collab. Stems stay local (FSA / OPFS) while the session document syncs to the collab server. Followers receive audio via WebRTC P2P from the leader. Designed in v1 but not built.

07 · Native plugins

Native plugins

Twelve native plugins in v1, all in one Rust workspace. Each compiles to a self-contained WASM module that satisfies the §16.03 contract. The host knows nothing about EQ vs. compressor vs. reverb — it just calls process().

Why Rust (in an otherwise JS stack)

The audio inner loop runs 48,000 times a second. AssemblyScript leaves performance on the table; hand-written C is unsafe; JS with WASM SIMD is a hack. Rust gives us:

  • Predictable, deterministic memory layout (no GC pauses)
  • SIMD via wasm32-unknown-unknown with simd128
  • Mature DSP crates: rustfft, biquad, dasp
  • Memory safety in code that runs in everyone's browser

The ship-gate benchmark

A headless Chrome process opens a synthetic 64-track session, runs 30 s of audio with full plugin chains, measures: audio-thread CPU %, UI thread frame time, total memory. If it regresses past the §16.07 threshold, merge blocks.

This is the single most important piece of CI infrastructure. Without it, we'd ship a bloated 32-track DAW by mistake.

The five canonical E2E suites

The five UX flows from brainstorm §20 become committed Playwright specs. They're the durable test of "does the product still work end-to-end after this change?"

apps/web/tests/e2e/
├── flow-1-first-mix.spec.ts          # empty → delivered · target < 2 hrs active
├── flow-2-quick-revision.spec.ts      # returning user · quick tweak
├── flow-3-stem-swap.spec.ts           # new stems · mix survives
├── flow-4-client-revisions.spec.ts    # snapshot + share-link round-trip
└── flow-5-mastering-arc.spec.ts       # single stereo bounce → mastered

Each suite drives a real browser, real audio playback (synthetic stems for determinism), and asserts against both visible UI state and audio output (silence ≠ output, hash matches expected, LUFS within tolerance).

DSP-specific testing

DSP is famously hard to test — output depends on continuous-valued state. Three approaches together cover it:

  • Golden outputs. Each plugin processes a committed 30 s reference signal (impulse + sweep + pink noise + music excerpt). The output WAV's hash must match the committed golden file. Catches accidental changes to DSP math.
  • Property-based sweeps. Random parameter values, random input — output must never NaN, never Inf, never exceed 0 dBFS by more than the plugin's declared headroom. Catches numerical bugs that golden tests miss.
  • Latency assertion. Each plugin reports its latency via latencySamples(). The host sums latencies across the chain and asserts the master output is delayed by exactly that amount. Catches latency-compensation regressions, which are otherwise invisible until two engineers compare notes.

What we measure that nobody else does

Real-user audio thread CPU. We emit a sample every 30 s from the AudioWorklet to the main thread, batched, sent to OTEL. Engineers don't tell us when audio breaks; the meter does. This is also the ground truth for the perf envelope (§16.07) — we'll see drift before it becomes a complaint.

14 · Risks

Risks & unknowns

The native plugin suite slips

12 high-quality plugins is six engineer-months minimum. If the DSP engineer is slower than that, we either delay v1 or ship a weaker plugin suite — and v1 needs the suite to be compelling.

Start the DSP engineer in month 1, not month 6. Port well-known open-source DSP (Faust libraries, JSFX scripts) as starting points rather than greenfield each plugin.

Audio thread regression hidden until production

A subtle change in the worklet (allocation in a hot path, a non-SIMD branch) can drop us from "smooth" to "popping" without changing any visible behavior.

The ship-gate benchmark (§16.07) runs on every PR. Block merge on regression. Real-user telemetry tracks audio-thread CPU over time so we see drift before users do.

Safari falls further behind on Web Audio APIs

If Safari ships partial AudioWorklet support or doesn't catch up on SharedArrayBuffer, we lose the second-most-common browser. Macs are common in audio circles.

Track WebKit nightly. Maintain a "Safari-degraded" code path. If it falls too far behind, consider a thin Electron wrapper as an emergency desktop fallback.

Scope creep — collab keeps trying to come back

Every "we could let two engineers..." idea pulls the v2 collab work into v1. Each individual ask is small; cumulatively they undo the scope cut and we ship neither solo-mixer-v1 nor real-collab-v2.

When a feature proposal needs > one open session at a time, it's v2. No exceptions in v1. Document the "v2 path" in the spec for that feature so it's clearly deferred, not lost.

"Free for everyone" + storage cost spiral

If cloud-mode usage skews higher than projected, R2 storage costs grow faster than any revenue can offset.

Default new sessions to Cloud (collab works) but make Hybrid + Local one click away on the import screen. Aggressive cold-tier + 1-year archive with email warning. If still unsustainable: cap free-tier active cloud sessions per user (Pro tier removes the cap).

Stem swap fingerprint collisions

If two stems sound similar (kick vs. floor tom in a sparse session), the fingerprint matcher might cross them. The blast radius is "wrong stem in wrong slot."

Require explicit confirmation for any match below 85%. Surface a side-by-side waveform comparison for uncertain matches. The session is reversible (snapshot pre-swap).

21 · Clip editing v1

Clip editing v1

The next v0.3 lane after the plugin marathon. Cut / move / trim per stem on the existing stem timeline (§02), with snapping and undo. Scope stays deliberately narrow: edits live inside a single stem — no cross-stem moves, no inserts, no MIDI. Today a stem is implicitly one region starting at t=0; MixState has no clip or timeline-position concept at all. This section maps the feature onto the code that exists.

Data model

A clip is a window into the stem's source buffer placed on the timeline, expressed in samples (sample-accurate; avoids float-seconds drift, and the engine already thinks in samples in getStemPeaks). It adds a per-channel clips array to ChannelStateSchema in packages/session-doc/src/mix-state.ts. An absent/empty array means "play the whole buffer at t=0", so old sessions stay correct with no rewrite. 

Clip = {
  id: string;             // stable — React keys, drag targeting, undo deltas
  sourceIn:      number;  // first source sample played      (trim-left)
  sourceOut:     number;  // one-past-last source sample     (trim-right)
  timelineStart: number;  // global-timeline sample of sourceIn (move)
}                          // refine: sourceOut > sourceIn

// ChannelStateSchema gains:  clips: Clip[]   (empty ⇒ whole buffer at t=0)
// MIX_STATE_VERSION: 15 → 16

Migration is client-side in hydrateMixState (apps/web/app/session/[id]/_mixer-shell.tsx): the field-by-field upgrade loop gains clips: c.clips ?? [], promoting every v1–v15 doc to an empty-clips v16. Normalise undefined → [] on the successful-parse branch too, so the engine and UI treat both identically.

The version cutover is the sharp edge

version is a z.literal, and the API strict-parses every save (MixStateSchema.parse in apps/api/src/sessions/sessions.service.ts). A v16 client autosaving against a v15 API gets a 400, and vice-versa. Ship the bump in packages/session-doc + apps/api together and before any web UI writes clips; widen to z.union([z.literal(15), z.literal(16)]) for the one transition release, then narrow back.

Timeline UI

The lane in _stem-timeline.tsx renders one continuous waveform today (StemLane → WaveCanvas, read-only). With a non-empty clips array, render N positioned .stem-clip rectangles inside the lane, each windowing the cached peaks to its [sourceIn, sourceOut) range — the empty-clips path keeps today's exact rendering.

  • Geometry from the shared globalDuration & sampleRate: leftPct = (timelineStart/sr)/globalDuration, widthPct = ((sourceOut−sourceIn)/sr)/globalDuration.
  • Move — drag the clip body; timelineStart changes, source window unchanged.
  • Trim-in — left handle; sourceIn and timelineStart move together so the audio stays anchored. Clamp sourceIn < sourceOut.
  • Trim-out — right handle; sourceOut moves. Clamp sourceOut > sourceIn and ≤ totalSamples.
  • Pointer events (setPointerCapture + window pointermove/up), not the lane's onClick seek. The full-width seek overlay (div.stem-timeline-track) must yield to clip drags via z-order / hit-testing while still seeking on empty regions — the trickiest wiring.
  • Snapping within ~6px (converted to samples), priority: timeline zero → sibling clip boundaries on the same lane → playhead → ruler ticks (reuse RulerMarks). Hold Alt to disable. No cross-lane/grid snap in v1.
  • Plumbing — clips live in channelState[stemId].clips in MixerShell; a new setClips(stemId, next) (sibling to setVolume) updates state (autosaves via the existing effect), pushes the engine update, and records one undo entry.

Audio engine

Move from "one source per channel" to one source per clip. Replace channel.source with channel.sources[] in packages/audio-engine/src/host.ts, add setChannelClips(stemId, clips) (write-through; re-schedule that channel if playing), and rewrite playAll(offset) to schedule each clip with the three-arg start(when, offset, duration) form — sample-accurate placement that auto-stops at the clip edge. 

playAll(offset):
  t0 = ctx.currentTime;   head = offset * sr
  for each channel:
    clips = channel.clips ?? [{ in:0, out:buffer.length, start:0 }]  // default = today
    for each clip:
      clipStart = start;   clipEnd = start + (out − in)
      if   clipEnd  <= head:   skip                                   // already past
      elif clipStart >= head:   src.start(t0 + (clipStart−head)/sr,    // fully ahead
                                          in/sr, (out−in)/sr)
      else:                     src.start(t0,                         // straddles playhead
                                          (in + head−clipStart)/sr,
                                          (clipEnd−head)/sr)
  • Seek needs no new logic — handleSeek already re-calls playAll(target), which re-derives the whole schedule (gap → next future clip; mid-clip → straddle case).
  • Duration — durationSeconds becomes max clipEnd across channels when clips exist, falling back to longest-buffer when empty (drives the ruler, playhead %, and the seek clamp).
  • Teardown — stopAll / isPlaying / removeChannel iterate sources[]; each source's onended clears only its own slot. The existing .stop() try/catch covers already-ended scheduled sources.

Undo / redo

None exists today (the atoms.ts dot-path machinery is a stub on a different doc). Introduce the smallest thing that fits the non-jotai mixer: a per-stem snapshot stack in MixerShell refs.

  • undoStack: { stemId, before: Clip[], after: Clip[] }[] + a mirror redoStack. v1 edits are always single-stem, so per-stem snapshots stay clean.
  • Capture before on pointerdown, push one entry on pointerup — a whole drag gesture is one undo step (no 60/s spam from pointermove).
  • undo()/redo() apply a snapshot through setClips, so autosave + the engine update ride along for free.
  • Keyboard at MixerShell level (Cmd/Ctrl+Z, +Shift for redo), guarded against firing while typing in inputs.

Risks & tricky bits

  • Version cutover — z.literal + strict server parse means no graceful skew without the z.union transition release. Stage the API before web.
  • Seek overlay vs. clip drags — the single full-width click-seek layer must yield to clip drag/trim without breaking click-to-seek over empty timeline.
  • Sample accuracy — store clips in samples, convert to seconds only at start(when, offset, duration); clamp offset/duration to buffer bounds.
  • Peaks on trim — window the cached peaks array by sample range at draw time; never call getStemPeaks per drag frame.
  • Old-session hydration — normalise undefined → [] at hydration so engine + UI treat "no clips" as one whole-buffer clip everywhere.
  • Duration redefinition — max-clipEnd shifts ruler / playhead / seek clamp; the empty-clips fallback must still report buffer length.
